# Start on Zap, Watch Blink 1.0
Up: [[Library]]

> Snapshot from 2026-09-20, kept verbatim for citations and detail. Current knowledge: [[Research/zap-vs-blink-recommendation]], [[Research/blink-published-benchmark-and-changes-since]]. If they disagree with this document, they win.

For a brand-new Roblox project starting in September 2026, **use Zap 0.6.29**. The deciding factor is not documentation, although Zap's docs are structurally better and your instinct there is sound; it is that Blink is mid-rewrite. Blink's stable line (**v0.18.9, released 2026-09-19**) has shipped only bug fixes since January and uses a syntax that will not carry into 1.0, while the rewrite (**v1.0.0-pre.10, same day**) has no documentation site, no working TypeScript output, and was still fixing basic correctness bugs (numeric ranges not enforced, a validation error corrupting the outgoing buffer) in the week before this report. Zap 0.6.x is also frozen, but frozen in the good sense: its author declared it "pretty much feature complete" in September 2024, its advertised rewrite has been dormant since July 2024 so no forced migration is coming, and studios run forked builds of it in production. The performance case for Blink rests almost entirely on Blink's own benchmark, which ran **Blink v0.17.1 against Zap v0.6.20 on 2025-04-30** and found an **8% client-FPS edge on a struct-array payload and 87% on a boolean-array payload, with identical bandwidth**; Zap's bitpacking (v0.6.24, July 2025) postdates that run and targets exactly the boolean case, so your re-run against Zap 0.6.29 and Blink 0.18.9 / 1.0.0-pre.10 will likely narrow the headline gap. Zap's real weakness is thin maintenance: one release in 2026, a memory-leak bug and a module-size bug sitting without maintainer reply, and a community fix closed unmerged. Blink is the better choice if you want a Studio-only workflow, need types Zap lacks (64-bit integers, f16, generics, two-way events), can patch a Luau codebase yourself, or if your re-run shows a CPU gap on your actual payload shapes that your game would feel; and the whole decision should be revisited the day Blink 1.0 ships stable with docs.

## Blink's two-track rewrite, not its docs, decides this

As of 2026-09-20 Blink has two parallel lines and neither is a comfortable target for a new project. The `0.18.x` line is what GitHub marks "Latest": v0.18.7 (2026-02-13), v0.18.8 (2026-04-11) and v0.18.9 (2026-09-19) are all bug-fix releases, and every new feature since January 2026 has landed only in the 1.0 pre-release track ([Blink releases](https://github.com/1Axen/blink/releases)). That 1.0 track opened with v1.0.0-pre.1 on 2026-01-14 as "The blink rewrite": all exports nested under a `.exports` table, unit enums replaced by string-literal unions, `Instance?` replaced by `StreamedInstance`, Promise/Future yield modes and `f16` removed, and a list of things "planned but not included" that ran to "Bit packing, stable structs, sync validation, TypeScript output, batch max size option, glob imports, destructured imports, and token bucket rate limiting" ([v1.0.0-pre.1](https://github.com/1Axen/blink/releases/tag/v1.0.0-pre.1)). The `rewrite` branch has no `docs/` directory at all; the syntax is learnable only from `examples/*.blink` and release notes ([rewrite tree](https://github.com/1Axen/blink/tree/rewrite)). The maintainer has not announced any 1.0 pre-release on the DevForum thread, whose last two announcements are 0.18.5 and 0.18.9 ([DevForum p.9](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671?page=9)).

The quality of that pre-release line a month ago is the sharpest evidence. On 2026-09-15 a single external tester filed roughly twenty issues against pre.7, including **#90 "Numeric ranges (e.g. u8(0..10)) are parsed but never enforced"**, **#91 "A validation error inside fire() leaves partial bytes in the outgoing buffer and corrupts the batch"**, #94 `vector(range)` crashing at runtime, #92 players present before the server module loads breaking reliable fires, #93 messages received before `on()` being silently dropped while the queue grows forever, and #98 the shipped `examples/generics.blink` failing to compile ([#90](https://github.com/1Axen/blink/issues/90); [#91](https://github.com/1Axen/blink/issues/91); [#92](https://github.com/1Axen/blink/issues/92); [#93](https://github.com/1Axen/blink/issues/93)). Issue #99 catalogued options in pre.7 that "compile without warnings but lack implementation", including the `typescript` option, `--watch`, `--profile`, `@stable` and `@bitpack`, and three different version strings across the CLI banner, tag and package manifest ([#99](https://github.com/1Axen/blink/issues/99)). To the maintainer's credit, pre.8, pre.9 and pre.10 shipped on September 16, 18 and 19 and closed most of that batch within days ([Blink releases API](https://api.github.com/repos/1Axen/blink/releases?per_page=5)). But a compiler that did not enforce declared numeric ranges in August is not something to build a new game's security boundary on in September, and there is no published target date for a stable 1.0 anywhere on GitHub, the docs, or the DevForum.

Choosing 0.18.9 instead does not escape the problem; it defers it. The 0.18 syntax (`struct Entity { ... }`, `event Foo { From: Client, ... }`, PascalCase options) is not the 1.0 syntax (`type entity = struct { ... }`, `event foo = { from: Client, ... }`, snake_case options, `blink.exports.foo.fire(...)`), and no migration guide exists in either direction ([types.blink](https://github.com/1Axen/blink/blob/rewrite/examples/types.blink); [remotes.blink](https://github.com/1Axen/blink/blob/rewrite/examples/remotes.blink)). A project that adopts 0.18.9 today is adopting a maintenance-mode API whose successor will require a schema rewrite and call-site changes across the codebase.

Zap's situation is superficially similar and substantively different. Its README still says "Zap is currently undergoing a rewrite" with 0.6.x maintained by sasial-dev, but the rewrite branch's last commit is "make CI run for all PRs" on 2024-07-07, twenty-six months ago, and its own README calls it "a early pre-release state" ([Zap README](https://raw.githubusercontent.com/red-blox/zap/0.6.x/README.md); [rewrite commits](https://api.github.com/repos/red-blox/zap/commits?sha=rewrite&per_page=5)). The practical reading is that **0.6.x is the product and no next-gen Zap is coming**, which for a new project is a feature: the v0.6.13 notes said "Zap `0.6.x` is pretty much feature complete at this point" back in September 2024, and breaking changes since have been rare and small (the v0.6.10 remote-path move, v0.6.17 dropping the ID parameter on unreliables, v0.6.24 deprecations that still compile with warnings, v0.6.28 making `Reliable` the default) ([v0.6.13](https://github.com/red-blox/zap/releases/tag/v0.6.13); [Zap releases API](https://api.github.com/repos/red-blox/zap/releases?per_page=100)). A `.zap` schema written today will still compile in a year. A `.blink` schema written today will need rewriting before it compiles on Blink 1.0.

## Zap's docs are broader; Blink's maintainer is more present

Your perception about documentation holds up against the structure of the two sites, even though no DevForum post was found saying so in as many words. Zap's VitePress site has nine content pages (What is Zap, Getting Started, Options, Types, Events, Functions, Generate Code, Generated API, Tooling) plus a live Monaco playground that recompiles on every keystroke and shows client, server, tooling and types output, and its Options and Types references carry per-feature version tags such as `types_output` [0.6.18+] and OR types [0.6.20+] ([Zap config.mts](https://raw.githubusercontent.com/red-blox/zap/0.6.x/docs/.vitepress/config.mts); [playground.md](https://raw.githubusercontent.com/red-blox/zap/0.6.x/docs/playground.md); [Zap Options](https://zap.redblox.dev/config/options)). Blink's site is ten to eleven short pages, the CLI page documents a single flag, the TypeScript option gets one sentence, the maintainer acknowledged in May 2025 that "The snippet on the docs had a mistake in it", an August 2025 issue about unreadable code blocks in light mode is still open, and a January 2026 user asked for YouTube tutorials because the docs were hard to learn from ([Blink docs](https://1axen.github.io/blink/); [Blink thread p.3](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671?page=3); [DevForum p.8](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671?page=8)). Zap's docs are not lavish either: there is no changelog file, no namespaces page (namespaces are documented only in PR #192), no CLI reference, and the Generated API page does not cover `SendEvents` or the Heartbeat flush mechanics ([PR #192](https://github.com/red-blox/zap/pull/192); [Generated API](https://zap.redblox.dev/usage/generated-api)). But "thin and accurate for the version you will run" beats "thin, partly wrong, and silent about the version under active development."

The honest counterweight is maintenance, where Blink is clearly the more alive project. Zap's 0.6.x branch saw zero commits from January through April 2026, four in May (one feature PR plus three dependabot bumps), one version bump in June, and nothing since; **2026 has produced exactly one release, v0.6.29 on 2026-06-23** ([0.6.x commits](https://api.github.com/repos/red-blox/zap/commits?sha=0.6.x&per_page=100); [releases/latest](https://api.github.com/repos/red-blox/zap/releases/latest)). Two 2026 bug reports have no visible maintainer reply: #216 (January 8), a silent `Player` memory leak when `Fire` is called after `PlayerRemoving`, for which a community fix PR #223 was opened in May and **closed unmerged on 2026-09-12**; and #225 (September 10), from a studio whose generated modules grew so large they "can't even get past bytecode generation before tripping the Roblox script execution timeout", forcing them to maintain a sharding fork ([#216](https://github.com/red-blox/zap/issues/216); [#225](https://github.com/red-blox/zap/issues/225); [PR search](https://api.github.com/search/issues?q=repo:red-blox/zap+is:pr)). Historically Zap was fast (issues closed same-day or within days through 2025), so this reads as a maintainer with less time rather than an abandoned project, but a new adopter should assume they may need to patch Zap themselves, and Zap is a Rust compiler, which raises the bar for a Luau-native team ([closed issues](https://api.github.com/search/issues?q=repo:red-blox/zap+is:issue+is:closed)).

Blink's maintainer, by contrast, answers DevForum questions same-day and turned around the September 2026 issue batch in one to four days, but the project is equally a one-person show: 1Axen authored 205 of roughly 232 counted contributions, the 1.0 track went silent from mid-April to late August 2026, and the two oldest open issues, #12 "Plugin lags with larger config files" (July 2024) and #45 "Server DOS via large buffer input" (May 2025), have sat sixteen to twenty-six months without a fix ([Blink contributors](https://api.github.com/repos/1Axen/blink/contributors?per_page=30); [Blink issues](https://github.com/1Axen/blink/issues); [#45](https://github.com/1Axen/blink/issues/45)). Both projects have a bus factor of one, and raw popularity is a tie (Zap 187 stars / 29 forks, Blink 182 / 36) ([Zap repo API](https://api.github.com/repos/red-blox/zap); [Blink repo API](https://api.github.com/repos/1Axen/blink)). The one adoption signal that separates them is that Zap's 2026 issues come from studios running patched builds in live games with servers "as old as several days", while Blink's 2026 issues come mostly from one power user auditing a pre-release ([#219](https://github.com/red-blox/zap/issues/219)).

Some risks are shared and should shape your architecture regardless of pick. Both compilers trust the incoming buffer length and iterate over it server-side, so an exploiter sending oversized buffers can stall a server: Zap #219 documents real production crashes and a custom throughput-mediation patch, Blink #45 describes the same attack and is unanswered ([#219](https://github.com/red-blox/zap/issues/219); [#45](https://github.com/1Axen/blink/issues/45)). Plan a per-player packet-size and rate guard at the RemoteEvent boundary on day one. Both warn that yielding in a sync callback causes "undefined and game-breaking behavior", both cap unreliable payloads at 1000 bytes, and both raise a deserialization error when a non-optional `Instance` resolves to nil on the receiving side ([Zap Events](https://zap.redblox.dev/config/events); [Blink Events](https://1axen.github.io/blink/language/5-events); [Blink Types](https://1axen.github.io/blink/language/4-types)).

On tooling the two split by workflow. For a Rojo + roblox-ts project Zap is the cleaner fit: `typescript = true` emits `.d.ts` at the same paths as the Luau output, with `typescript_enum` (0.6.24+) and `typescript_max_tuple_length` tunables, and v0.6.29 allows requiring the client module from Studio edit mode for Storybook-style UI tooling ([Zap Options](https://zap.redblox.dev/config/options.html); [releases/latest](https://api.github.com/repos/red-blox/zap/releases/latest)). Blink 0.18 also emits TypeScript, but the 1.0 pre-releases accept the option and generate nothing, and the equivalent edit-mode request (#81) is still open ([#99](https://github.com/1Axen/blink/issues/99); [Blink issues](https://api.github.com/repos/1Axen/blink/issues?state=open&per_page=20&sort=created&direction=desc)). For a Studio-first workflow Blink is the only one with an official plugin, and its install story is more modern (`rokit add 1Axen/blink`, pesde from 0.18.5) where Zap's docs still say Aftman ([Blink Installation](https://1axen.github.io/blink/getting-started/1-installation); [Zap install](https://zap.redblox.dev/install.html)). Both have community VS Code extensions, and Blink's is a fork of Zap's ([blink-vscode](https://github.com/1Axen/blink-vscode)).

## The published benchmark pitted Blink 0.17.1 against Zap 0.6.20

The only first-party comparison is `benchmark/Benchmarks.md` in the Blink repo, linked from the README, the docs home and the DevForum post. Its header reads "Updated: 2025-04-30 19:45:09 UTC" with **blink v0.17.1, zap v0.6.20, bytenet v0.4.3**, on an AMD Ryzen 9 7900X with two 17 GB memory modules at 4800 ([Benchmarks.md](https://raw.githubusercontent.com/1Axen/blink/main/benchmark/Benchmarks.md)). Both libraries were the newest available that day: Blink v0.17.1 had shipped on 2025-04-29 and Zap v0.6.20 on 2025-04-13, consistent with the harness's `download.luau` always pulling `releases/latest` ([v0.17.1 API](https://api.github.com/repos/1Axen/blink/releases/tags/v0.17.1); [Zap releases API](https://api.github.com/repos/red-blox/zap/releases?per_page=100); [download.luau](https://github.com/1Axen/blink/blob/main/benchmark/download.luau)). The file has been touched exactly three times: the original layout (2024-08-10, recording a 2024-05-06 run with blink v0.11.1 and zap v0.6.3), the 2025-04-30 re-run, and a line-ending conversion on 2025-10-24 that changed no numbers ([Benchmarks.md history](https://github.com/1Axen/blink/commits/main/benchmark/Benchmarks.md); [Benchmarks.md @720048b](https://raw.githubusercontent.com/1Axen/blink/720048b/benchmark/Benchmarks.md)).

| | Published benchmark (2025-04-30) | Current as of 2026-09-20 |
|---|---|---|
| Zap | v0.6.20 (2025-04-13) | **v0.6.29** (2026-06-23); nine releases later |
| Blink stable | v0.17.1 (2025-04-29) | **v0.18.9** (2026-09-19); GitHub "Latest" |
| Blink pre-release | none | **v1.0.0-pre.10** (2026-09-19); tenth pre-release since 2026-01-14 |
| ByteNet (out of scope) | v0.4.3 | not researched |

The method is a client-side stress test run inside Roblox Studio via `run-in-roblox`. For each library and each of two payloads, the client fires the reliable event **1000 times per `PostSimulation` frame for 10 seconds using the same pre-built table every time**, sampling client frame rate and `Stats.DataSendKbps` once per second and reporting median, P0, P80, P90, P95, P100 and packet loss ([init.client.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/client/init.client.luau)). The payloads are an "Entities" array of **100** six-`u8` structs (`id, x, y, z, orientation, animation`, random 1..255, unseeded) even though the schema allows `Entity[0..1000]`, and a "Booleans" array of 1000 literal `true` values; both events are `Reliable` with `SingleSync` callbacks ([Definition.zap](https://github.com/1Axen/blink/blob/main/benchmark/definitions/Definition.zap); [Definition.blink](https://github.com/1Axen/blink/blob/main/benchmark/definitions/Definition.blink); [Entities.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/shared/benches/Entities.luau); [Booleans.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/shared/benches/Booleans.luau)). Neither adapter wraps the generated code, so Zap ran with its defaults, including `write_checks = true` and the automatic Heartbeat flush, and Blink ran with its automatic per-frame replication, which v0.17.1 had just uncapped from 60 Hz the day before ([modes/zap.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/shared/modes/zap.luau); [Zap Options](https://zap.redblox.dev/config/options.html); [v0.17.1](https://github.com/1Axen/blink/releases/tag/v0.17.1)).

| Scenario | Metric | Blink 0.17.1 | Zap 0.6.20 | ByteNet 0.4.3 | Roblox |
|---|---|---|---|---|---|
| Entities | Median FPS | **42** | 39 | 32 | 16 |
| Entities | Median Kbps (60-FPS normalized) | 41.81 | 41.71 | 41.64 | 559,364 |
| Booleans | Median FPS | **97** | 52 | 35 | 21 |
| Booleans | Median Kbps (60-FPS normalized) | 7.91 | 8.10 | 8.11 | 353,107 |

Packet loss was 0% in every cell ([Benchmarks.md](https://raw.githubusercontent.com/1Axen/blink/main/benchmark/Benchmarks.md)). Relative to Zap, Blink is **+7.7% on Entities and +86.5% on Booleans**; the Booleans gap is the headline and, as the next section shows, the one most exposed to what has changed since. The README's "1.6-3.7x faster than ROBLOX" does not match these tables (42/16 is 2.6x, 97/21 is 4.6x) and appears to predate the 2025 re-run ([README](https://github.com/1Axen/blink)).

Read the numbers for what they are. The FPS column captures the client cost of 1000 `Fire` calls per frame plus, because Studio play mode runs client and server in one process, the server's deserialization of those packets; it is not an isolated serialize or deserialize microbenchmark, and only the first packet per run is content-validated. The Kbps column is not an encoding-size comparison at all: sending an identical buffer 1000 times per frame is extremely compressible at the transport layer, which is why three different encodings land within 0.2% of each other and four to five orders of magnitude below native Roblox, and why the author himself conceded in May 2024 that "the faster something runs the higher the kbps is" before adding the `60 / Frames` normalization ([init.client.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/client/init.client.luau); [Blink thread p.1](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671)). Ten samples per run also make the percentiles coarse. No Zap maintainer has publicly critiqued or disputed the results, and Zap publishes no benchmarks of its own ([Zap issues](https://github.com/red-blox/zap/issues)). The one independent 2025 comparison, from the Packet library thread on 2025-04-04 using Zap 0.6.19 and Blink 0.17.0, concluded only that "blink is slightly better than zap" ([Packet thread #99](https://devforum.roblox.com/t/packet-networking-library/3573907/99)). Nothing from 2026 was found.

## Bitpacking, inlining and SyncValidation will move a re-run

Nine Zap releases separate the benchmarked v0.6.20 from today's v0.6.29, and three of them touch the exact hot paths this harness exercises. **v0.6.22 (2025-06-24) inlines resolved types where possible**, which removes a function call per `Entity` in the array loop (100 per fire, 100,000 per frame in the Entities scenario) ([Zap releases](https://github.com/red-blox/zap/releases)). **v0.6.24 (2025-07-11) added bitpacking (#198) and separated "is empty" from length serde (#201)**; if bitpacking covers `boolean[]`, which the release note does not enumerate, a 1000-boolean array shrinks from roughly 1000 bytes to roughly 125 and each element write becomes a bit operation, directly attacking the scenario where Blink led by 87% ([v0.6.24](https://github.com/red-blox/zap/releases/tag/v0.6.24)). **v0.6.25 (2025-07-21) fixed a bitpacking mismatch**, so nothing older than that should be used to test the feature ([Zap releases API](https://api.github.com/repos/red-blox/zap/releases?per_page=100)). The remaining releases are neutral for this test: v0.6.21 namespaces, v0.6.26 duplicate-instance validation, v0.6.27 a fix for buffer out-of-bounds with 256+ concurrent function calls, v0.6.28 microprofiler labels (`include_profile_labels`, default false, and it must stay false in the comparison run) plus `Reliable` as the default event type, and v0.6.29 edit-mode requires. Nothing in the window changed `manual_event_loop`, the Heartbeat flush, or the `write_checks` default of `true`. Verify the bitpacking effect directly by inspecting the `Booleans` writer in the `Client.luau` that Zap 0.6.29 generates before trusting any FPS delta.

Blink's changes split by line. On **0.18.x**, the u8-struct and boolean-array serialization paths have no listed changes since v0.17.1, so a v0.18.9 run should land near the 2025 Blink numbers with one caveat: **`SyncValidation` became on-by-default in v0.18.5 (2025-10-24)**, and it emits code that checks for yielding in sync callbacks, which is exactly the `SingleSync` receive path both benchmark events use ([Blink releases p.2](https://github.com/1Axen/blink/releases?page=2); [Blink Options](https://1axen.github.io/blink/language/1-options)). v0.18.7 (2026-02-13) removed redundant instance assertions and fixed an "out of local registers" failure from too many serdes functions, and v0.18.9 fixed NaN values bypassing range validation; neither touches this payload ([Blink releases](https://github.com/1Axen/blink/releases)). On **1.0.0-pre.x**, the relevant items are pre.4 (2026-02-09) no longer sending an empty buffer every frame, pre.5 (2026-03-15) batched events no longer exiting early, **pre.6 (2026-04-11) "Optimized array reads"**, which is precisely the receive path for `Entity[]` and `boolean[]`, **pre.9 (2026-09-18) optimizing enum storage and disabling write validations in the `release` profile**, and pre.10 tightening bounds validation ([v1.0.0-pre.9](https://github.com/1Axen/blink/releases/tag/v1.0.0-pre.9); [Blink releases](https://github.com/1Axen/blink/releases)). Notably, bitpacking is still absent from 1.0: pre.8 removed the `bitpack` attribute as stale and issue #105 "Implement @bitpack annotation" is open, so the boolean scenario is where Zap has gained a structural optimization Blink has not ([Blink issues](https://github.com/1Axen/blink/issues)).

| Library and version | Change | Expected effect on this harness |
|---|---|---|
| Zap v0.6.22 | Inline resolved types | Fewer calls per `Entity`; Entities FPS up |
| Zap v0.6.24 / v0.6.25 | Bitpacking; separate is-empty/length serde; mismatch fix | Booleans bytes and CPU down, likely the largest single mover |
| Zap v0.6.28 | `include_profile_labels`, `Reliable` default | Neutral if labels stay off; per-event timings available for diagnosis |
| Blink v0.18.5 | `SyncValidation` default on | Small added cost on the `SingleSync` receive side |
| Blink v0.18.7 / v0.18.9 | Register-exhaustion fix; NaN validation | Neutral for u8/boolean payloads |
| Blink 1.0.0-pre.6 | Optimized array reads | Receive-side speedup on both scenarios |
| Blink 1.0.0-pre.9 | Write validations off in `release`; enum storage | Send-side speedup in `release`; default profile may be slower than 0.18 |
| Blink 1.0 (all) | No bitpacking (#105 open) | Booleans encoding unchanged from 0.x |

Several mechanics of the harness matter for a faithful re-run. `download.luau` resolves `releases/latest` for both tools, so an unmodified run will pull **Zap 0.6.29 and Blink 0.18.9**, never a 1.0 pre-release, which must be pinned by hand; it also fetches ByteNet, which you can leave in or drop from `modes/` ([download.luau](https://github.com/1Axen/blink/blob/main/benchmark/download.luau)). `Definition.zap` uses no syntax that v0.6.24 deprecated (no bare `string` or `Instance (X)`), so it compiles unchanged on 0.6.29, and `Definition.blink` is 0.x syntax that compiles on 0.18.9. Running Blink 1.0 requires porting the definition to `type Entity = struct { ... }` and `event Booleans = { from: Client, ... }` form, choosing a profile, and updating the harness, because the client selects a firing method via `Event.Fire or Event.send` and the server via `Event.On or Event.SetCallback or Event.listen`, while 1.0 exposes `blink.exports.<event>.fire` and lowercase, `.exports`-nested handles ([init.client.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/client/init.client.luau); [init.server.luau](https://github.com/1Axen/blink/blob/main/benchmark/src/server/init.server.luau); [v1.0.0-pre.1](https://github.com/1Axen/blink/releases/tag/v1.0.0-pre.1)). Two fairness variables deserve explicit configurations rather than defaults: Zap's `write_checks` defaults to `true` and its docs describe it as a setting to disable in production, whereas Blink 0.18's `WriteValidations` defaults to `false` and Blink 1.0's `release` profile strips write validation entirely, so report Zap both with and without `opt write_checks = false` ([Zap Options](https://zap.redblox.dev/config/options.html); [Blink Options](https://1axen.github.io/blink/language/1-options)). Whether Blink 0.17.1 performed any write-side validation in the published run could not be established. Record the Roblox Studio version, which the 2025 run did not, and treat Kbps as a sanity check only; if you want a real encoding-size comparison, measure `buffer.len` of the flushed packet per frame instead, since the harness's identical-payload design makes `DataSendKbps` compression-dominated.

## When Blink is the better choice

The recommendation flips under a handful of concrete conditions. **If your workflow is Studio-only with no external toolchain**, Blink is the only option with an official Creator Store plugin that writes and generates definitions inside Studio; Zap's equivalents are a community plugin (Zappy) and the web playground ([Blink Plugin](https://1axen.github.io/blink/getting-started/4-plugin); [Zap Getting Started](https://zap.redblox.dev/intro/getting-started.html)). Weigh that against the plugin editor freezing at 150 to 800 lines of schema (issue #12, open since July 2024) and a user hitting Studio's 200,000-character source limit with a generated module ([DevForum p.4](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671?page=4); [DevForum p.9](https://devforum.roblox.com/t/blink-an-idl-compiler-written-in-luau-for-roblox-buffer-networking-0185/2959671?page=9)).

**If your schema needs types Zap does not have**, Blink is ahead. Zap has no 64-bit or 24/40/48/56-bit integers (open request #67 since February 2024), no documented generics, and no two-way events ("Zap does not support two way events") ([Zap issues](https://github.com/red-blox/zap/issues); [Zap Events](https://zap.redblox.dev/config/events)). Blink 0.18 offers `f16`, struct and enum generics, per-component `CFrame<i16, f16>` and `vector<u8>` encodings, and multi-file `import`; Blink 1.0 adds `u24`/`u48`, a flagged `integer` (int64), union types and recursive generic types, `from: Both` events and `StreamedInstance`, while dropping `f16`. Zap is not bare here: it has had OR/union types since v0.6.20 and supports recursive types, so the gap is generics and integer widths, not unions ([Blink Types](https://1axen.github.io/blink/language/4-types); [types.blink](https://github.com/1Axen/blink/blob/rewrite/examples/types.blink); [Blink releases](https://github.com/1Axen/blink/releases)). Zap's own exclusives are `AlignedCFrame`, ordered unreliables, `FireSet`, and a documented tooling deserializer for PacketProfiler-style inspectors ([Zap Types](https://raw.githubusercontent.com/red-blox/zap/0.6.x/docs/config/types.md); [tooling.md](https://raw.githubusercontent.com/red-blox/zap/0.6.x/docs/usage/tooling.md)).

**If you expect to patch your networking compiler yourself**, Blink's Luau/Lute codebase is far more approachable for a Roblox team than Zap's Rust, which is likely why Blink has more forks despite fewer stars, and why Zap's unanswered 2026 bugs are a heavier liability for a team that cannot build Rust ([Blink repo API](https://api.github.com/repos/1Axen/blink); [Zap repo](https://github.com/red-blox/zap)). Related: if you value a maintainer who answers within a day over a frozen codebase, and are prepared to pin Blink 0.18.9 today and absorb the 1.0 migration later, that is a defensible bet on velocity that Zap cannot match right now.

**If your re-run shows a CPU gap you would actually feel**, let the data override this report. The threshold is not "Blink is faster" but "Blink is faster on payloads shaped like my hot path, at fire rates my game reaches, by enough to matter on my minimum-spec client". The published 8% Entities gap is within what most games will never notice; the 87% Booleans gap is the kind of number that matters for a flag-heavy replication scheme, and it is the number most likely to shrink once Zap's bitpacking is in the loop. Bandwidth is a wash by every measurement found, so do not choose on that axis.

Finally, **if Blink 1.0 reaches a stable, documented release before you write your first event**, re-run this analysis. Most of Zap's structural advantages (a frozen IDL, better docs, working TypeScript) are advantages over a pre-release, not over a finished Blink 1.0, and the 1.0 type system is meaningfully richer than Zap's.

## Conclusion

The real choice here is between two frozen APIs with opposite failure modes. Zap 0.6.x is frozen by neglect but stable in practice: its risks are slow bug fixes, a Rust barrier to self-service patches, and a monolithic-module ceiling that large games have already hit and forked around. Blink 0.18.x is frozen by design while its successor is built in public, and its risk is that everything you write today is on a deprecated syntax with an unscheduled, undocumented migration ahead. For a project starting now, the first kind of frozen is cheaper, and the migration cost between the two IDLs (schema file plus call-site names, not game logic, since both emit the networking layer as generated modules behind event handles) is modest for a small schema, so the decision is reversible early and gets more expensive with every event you add.

The benchmark re-run is worth doing, but frame it correctly: it will mostly tell you whether Zap's July 2025 bitpacking erased Blink's boolean lead, and whether Blink 1.0's release profile buys back the difference by dropping write validation. It will not tell you which library is safer to build on for two years, which is the question that should decide a brand-new project, and which today favors Zap. Put a per-player packet guard in front of whichever you pick, watch Zap #216 and #225 for a maintainer response, and set a reminder to look at Blink again when a `v1.0.0` tag without a `-pre` suffix appears alongside a docs site.
